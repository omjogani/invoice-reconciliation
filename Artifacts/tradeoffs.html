Freight Reconciliation Tradeoffs

The system decides which carrier invoice lines get paid, disputed or escalated. Money moves on its output, so every choice below starts from one question: can we trust the number?

What matters to us

Correct money

Every amount is calculated by code, never written by an AI model.

Same answer every run

Run it twice on the same data and get the same amounts and decisions.

Never guess

If the contract doesn't say, the line is escalated to a person, not priced by assumption.

Explainable

Each decision points to the contract clause behind it, and each exception gets a memo.

People stay in control

A person approves how each contract is read before it is used to price anything.

Grows with volume

More invoices or new carriers should not mean rewriting the system.

What we prioritized

When two goals pulled in different directions, the higher one won.

  1. Correctness over coverage

    We would rather escalate a line than pay or dispute it on a guess.

  2. Repeatable over clever

    AI reads text; code does the maths, so results don't drift between runs.

  3. Checked over trusted

    Every AI output passes a code check before the next step uses it.

  4. Clear over short

    Reports and memos explain the reason, even when that makes them longer.

  5. Speed and cost last

    Extra checks and a second contract reader cost time; we accept that.

What we took care of
Different invoice formatsText, JSON and CSV invoices are turned into one common format and totals are tied out.
Gaps in a contractA weight the contract doesn't cover is escalated with the possible prices, never picked.
Duplicate billingA shipment billed twice keeps one charge; the extra copy is disputed.
Credit notesCredits are counted against the original charge; a partial credit leaves the rest disputed.
Unknown referencesA line with no matching booking is escalated; likely matches are shown only as hints.
Volume discountsA missing discount is found from shipment counts and raised on the invoice.
Dispute deadlinesDeadlines are shown as dates in memos; they never change a decision.
Contract changesAn edited contract no longer matches its approved reading, so the run stops for review.
AI mistakesQuotes must exist in the contract, two readings must agree, and the reviewer can't lower a decision or change an amount.
The options we weighed
Option A

AI does everything

An AI agent reads invoices and contracts and works out every amount.

Good
  • Quick to build
  • Handles any document format
Bad
  • Numbers can change between runs
  • Arithmetic slips are hard to spot
  • Hard to audit why a line was disputed

Not chosen. We can't let an AI model write the numbers that decide payments.

Option B

Code does everything

A developer types each contract's rates into config, and code does the rest.

Good
  • Fully repeatable
  • Cheap and fast to run
Bad
  • Every contract is translated by hand
  • A changed contract goes unnoticed
  • No written explanation for exceptions

Not chosen. The hand translation is the risky step, and nothing checks it.

Option C · chosen

Code calculates, AI reads, gates check

AI turns each contract into a structured rate card and reviews exceptions. Code does all parsing, matching and maths. A code check sits between every step, and a person approves each rate card once.

Good
  • Numbers are exact and repeatable
  • Contract reading is automated but verified
  • Contract changes are caught
  • Every decision has a reason and a memo
Bad
  • More moving parts
  • Slower and costs more per run
  • A new contract needs a person's approval

Chosen. It keeps the AI where it is strong, reading text, and keeps it away from the money.

What we gave up

  • Each run takes longer, because contracts are read twice and every output is checked.
  • Some lines end up escalated to a person instead of decided automatically.
  • A new or edited contract waits for a person to approve its rate card.

For a system that decides payments, these costs buy correctness and trust.
